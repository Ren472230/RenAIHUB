## 2. Выбранная линия развития

**Сначала локальная установка общей серверной архитектуры, затем размещение серверных компонентов в облаке.** Это позволяет проверить UX и сценарии без ранних расходов и сохранить переход к подписке.

Целевая схема:

1. **Клиент:** браузерный рабочий интерфейс; настольный клиент – дополнительный адаптер для локальных файлов и возможностей ОС.
2. **Единый API:** авторизация, проекты, бизнес-сценарии, контроль действий, управление ИИ-провайдерами, лимиты.
3. **Сервис сценариев:** извлечение данных → схема/валидация → проверяемый расчёт → предварительный результат → утверждение → экспорт.
4. **Данные:** PostgreSQL для пользователей, организаций, проектов, истории, квот; отдельное защищённое хранилище файлов (локальное на P1, объектное или эквивалент на P2).
5. **Операции:** журнал событий, измерение расходов, резервные копии, мониторинг.

**Локальный режим:** браузер/desktop → локальный API → локальная БД. Вызовы облачных моделей остаются сетевыми, если явно не внедрена локальная модель. Не обещать полностью автономную офлайн-работу.

**Облачный режим:** браузер/desktop → HTTPS → API → общая инфраструктура с жёстким разделением организаций. Локальная установка и облако должны использовать одинаковые контракты бизнес-сценариев.

## 3. Сохранить или заменить – решение только после P0

Приоритет – сохранить Fastify/API, структуру моделей и пригодные части Tauri/Next.js, если аудит покажет оправданность. Следует проверить:

- возможность отделить обычный пользовательский интерфейс от административного;
- отсутствие зависимостей от старых офисных IP и прежней компании;
- безопасность авторизации и серверного хранения ключей;
- корректность потоков документов и прав локальных файлов;
- формат хранения чатов/проектов и возможность будущего tenant_id;
- обновления desktop и выполняемые системные команды;
- воспроизводимую установку, миграции и минимальные тесты.

**Критерий перепроектирования:** обнаружены существенные архитектурные препятствия, которые дороже безопасно исправить, чем заменить конкретный модуль. Решение фиксируется с оценкой альтернатив; тотальная перепись без этого запрещена рабочим принципом.

## 4. Модель доступа

### Личная версия P1
Один владелец и его локальные проекты. Требуются авторизация или равноценная защита доступа, безопасное хранение секретов, запрет действий агента вне разрешённого каталога.

### Облачная версия P2
Модель сущностей: Organization → Membership/Role → Project → Document/Conversation/UsageEvent.

Роли: владелец платформы (техническое управление), администратор организации, участник организации; поддержка без доступа к содержимому клиентов по умолчанию.

- Сервер определяет organization_id из проверенной сессии/членства; клиент не может назначить себе чужую организацию.
- Все запросы к данным, хранилищу и действиям проверяют принадлежность и права.
- Тесты включают попытки читать, менять, экспортировать и удалить чужие данные через API.
- Технический администратор видит метрики состояния и расходы без чтения контента компаний по умолчанию.
- Разграничение доступа проверяется **до** приглашения внешних организаций.

Не считать текущую схему User / Project / Conversation достаточной для изоляции арендаторов без дополнительных полей и проверок.

## 5. Безопасность и эксплуатация – обязательные контроли

| Риск | Минимальное требование | Проверка |
|---|---|---|
| Утечка API-ключей | Серверное хранение, шифрование/секретное хранилище, скрытие в логах, ротация | Просмотр сетевых запросов и журналов |
| Выполнение действий агентом | Белый список инструментов, ограничение путей, права на чтение/запись, подтверждение изменений | Негативные тесты на выход из папки и запись без разрешения |
| Враждебные инструкции в файлах | Считать загружаемый контент недоверенным; не исполнять найденные команды | Тест с документом, содержащим попытки перенаправить агента |
| Небезопасные обновления | Проверка подлинности, подписи/хеша, источника и явное управление установкой | Тест подменённого пакета |
| Утечка между компаниями | Серверный RBAC и разделение данных/файлов/кэшей | Cross-tenant API-тесты |
| Потеря данных | Резервные копии и восстановление; определённое хранение и удаление | Тест восстановления и очистки |
| Неограниченный счёт за API | Учёт каждого запроса, бюджеты, ограничения и аварийная остановка | Нагрузочный тест и сценарий исчерпания квоты |
| Перегрузка/атаки | Ограничения запросов, размера файлов, тайм-ауты и валидация | Негативные тесты |
| Наблюдаемость | Минимизация персональных данных в журналах; события без исходных документов | Аудит логов и ролей доступа |

Требования к защите персональных данных и правилам обработки внешними модельными провайдерами проверяются по целевой юрисдикции до коммерческой эксплуатации.

## 6. Контракт первого бизнес-сценария

**Вход:** текст заявки и/или документ, идентификатор проекта, версия шаблона, настройки допустимого провайдера, явные расчётные параметры.

**Этапы обработки:**
1. Парсинг и нормализация данных с указанием исходного места.
2. Извлечение структурированных полей через ИИ и валидация формата.
3. Список пустых и спорных данных – пользователь исправляет/подтверждает.
4. Расчёты отдельным детерминированным модулем с фиксированными формулами и единицами.
5. Черновик предложения с раскрытыми допущениями.
6. Просмотр/правка/подтверждение пользователем.
7. Экспорт редактируемого результата и запись метаданных версии.

**Выход:** документ, версия входа, версия шаблона, протокол вычислений, список допущений, идентификатор выполнения, токены/стоимость обработки.

**Инвариант:** модель не становится источником «истинных» чисел без сверки; отсутствие цены/даты/условия нельзя маскировать выдуманным значением.

## 7. Сервис стоимости и подписок

### P1 – учёт стоимости
Каждый вызов сохраняет минимум: идентификатор выполнения/проекта, провайдер, модель, входные/выходные токены (или эквивалент тарификации), единицу/источник цены, зафиксированную стоимость и статус операции. Данные о ценах обновляются с датой действия; прогноз и факт разделяются.

### P2 – бюджеты организаций
Ограничения по организации, пользователю и периоду, уведомления и запрет превышения. Администратор платформы видит агрегаты; пользователь – свою квоту.

### P3 – биллинг
Тариф, статус подписки, доступные функции и квоты формируются отдельно от провайдера оплаты. Платёжный сервис выбирается только после проверки юрисдикции, договоров, комиссий и реального спроса.

## 8. План проверки архитектуры

**P0:** инвентаризация / права / секреты / зависимости / sandbox-запуск и сборка / базовый API health / проверка локального пути.  
**P1:** тесты одного сценария, стабильности сохранения и экспорта, ограничения агента, себестоимости и качества.  
**P2:** сквозные тесты организации/прав, сетевой безопасности, почты, резервирования и восстановления, нагрузки.  
**P3:** интеграционные тесты подписок, отключения доступа, возвратов/ошибок и поддержки.

Не подключать облачную инфраструктуру и почтового провайдера как предварительное условие **первого** локального сценария.
